# 翻译系统深化方案：从产出译文到可核验的翻译决策

日期：2026-10-18。代码观察基线：`90fbbd5`。本文是重写前的设计建议，不是已实现功能或真实翻译质量报告。

## 目标与边界

项目已有异步翻译、章节感知分块、文档画像、术语表、选择性修复、缓存、人工审校界面和评测框架。深化的目标是：关键译法能回溯原文，错误能被定位，修复增益能独立检验，尚未核验的内容不会被表述成已确认正确。

“可确”在这里理解为可核验、可追溯、有独立证据支持。不能用测试通过、多个模型同意或一份人评报告证明任意文本绝对正确。还应区分两件事：译文忠于原文，与原文中的科学或哲学主张成立。翻译系统不应为了“事实更正确”擅自修正作者的主张。

优先选一个范围做深，例如机器学习论文中的方法与实验部分；已有哲学阅读与审校资源更多时，也可先选一个作者的单本作品。两类文本应分别报告结果，不能用一个混合总分宣称都已解决。

## 一、专家通常会额外做什么

这里的“专家”指资深领域译者、学术编辑和翻译评估研究者组合后的审校做法，不假设每个专家使用同一流程。

1. **先明确翻译契约。** 读者、用途、版本、直译程度、引文处理、作者自造词与双关、脚注、代码和公式、允许注释的范围都要先定。哲学文本的含混可能应保留；技术论文的 may、only、unless、相关/因果、训练/测试不能被“润色”掉。
2. **先审源文。** 核对版本、阅读顺序、脚注归属、公式、图表和缺页。转换结果只能是一个待核验的中间产物。源文识别有误时，应先修源文并使相关译文过期，而非要求译者猜测。
3. **建立有依据的术语决策。** 记录概念定义、作者用例、章节范围、同形异义、备选译法、反例和决定者。统一译法只是目标的一部分；必须先确认其在该语境下成立。
4. **逐命题核对。** 检查谁对谁做什么、否定作用域、条件、量词、论证强度、指代、遗漏和增译。不能让中文流畅度抵消原意被改变。
5. **查看跨块关系。** 一个缩写首次定义后如何使用，this/it 指向什么，后文如何限定前文，一个作者是否有意变换同一词的含义。采样摘要不能保证覆盖这些关系。
6. **检验审校自身。** 保存初译和修订稿，检查修复是否引入新错；允许“无法判定”，把有理由的分歧留给领域审校者。
7. **建立外部证据。** 冻结评测集，隐藏系统身份，独立标注错误，记录分歧及仲裁，用人工结果校准自动指标。

这些建议的研究依据与适用限制见 [一手来源研究](translation-quality-primary-sources.md)。

## 二、从哪些原始素材开始

| 问题 | 优先素材 | 需要留存的定位与身份 |
| --- | --- | --- |
| 书到底写了什么 | 指定版次的原书 PDF/扫描页或原生 EPUB；作者/出版社勘误 | 文件 SHA-256、版次、页码；EPUB 的 spine、XHTML 路径和元素位置 |
| 论文到底主张什么 | 作者发布的明确版本论文、可得的 LaTeX 源、附录、补充材料、勘误 | DOI/arXiv ID 及版本、页码、节号、公式/表格编号 |
| 术语在作者处是什么意思 | 当前作品中的全部相关出现、作者自定义段落、引用作品原文；相关作者原著 | 原文片段、出处、定义位置、适用语境与冲突证据 |
| 实验数字与算法指的是什么 | 原始表格/图注、符号定义、算法伪代码；涉及实现时再查论文对应代码版本 | 单元格/图号、指标/数据集、单位、代码 commit；仅用于理解与核对，不能替作者改文 |
| 当前系统错在哪里 | 未经人工润色的初译、原始模型响应、自动修复前后版本、人工编辑差异 | 配置/提示词/模型身份、运行 ID、对应原文及译文版本 |
| 怎样才算翻对 | 由领域审校者直接依据原文制作的错误标注与可接受译法说明 | 匿名标注、错误跨度、类型/严重性、理由、分歧与仲裁 |

已经整理好的 Markdown、平面术语表和文档画像都可以继续使用，但属于派生材料。已有中文译本可辅助发现问题，需核对版本；不能把它当成唯一真值。模型生成的参考译文、术语解释和推理文字也不是外部证据。

只提供 Markdown 时，应如实记录“源材料仅为 Markdown，无法核验原版版面”；不能补造页码或声称完成了扫描页核对。版权受限的原书可在本地评测并保留哈希和访问说明；可公开的小样本另用许可清楚的真实材料。

## 三、仓库中已确认的缺口

| 观察 | 依据 | 对结论的影响 |
| --- | --- | --- |
| 规则质检不判断命题语义 | `src/core/validator.py`；下文反例 | 通过规则只说明未发现这些规则覆盖的问题 |
| 规则通过就不进入修复；关闭 QA 返回 passed=True | `src/pipelines/translate/quality_pipeline.py` | 语义漏检会绕过审校；未检查状态需要与通过区分 |
| 修复按规则严重性总分选择，持平也接受 | `TranslationValidator.is_better` | 减少表面问题或分数持平不能证明语义改善 |
| 数字比较使用集合，结构检查主要计数 | `src/core/validator.py` | 不能验证数字角色/方向/重复次数，也不能验证同数量链接的目标和代码内容 |
| 术语映射是字符串，按子串匹配 | `src/domain/rules/glossary_selection.py`、validator | 难表达义项、适用范围、依据及合法变体；机械统一可能统一地译错 |
| 文档画像为首中尾采样和字符串提示 | `document_analyzer.py`、`document_sampling.py`、`DocumentProfile` | 提示未携带出处；不能据此声称全书指代与定义已被覆盖 |
| 评测仅两篇自撰摘选，已提交报告为 dry-run | `docs/evals/methodology.md`、`datasets/dataset.json`、`results/README.md` | 有框架可用，尚无真实专业文本的质量增益证据 |
| 裁判缺维度会填 3 分，综合分取三维均值 | `src/evaluation/judge.py`、`models.py` | 缺失评测可能被当成真实中等表现；严重错译可能被流畅度平均掩盖 |
| 重复短语的一致性由整块译文公共子串判断 | `src/evaluation/consistency.py` | 无关相同文本可造成假一致；不能据此直接作 RAG 架构决定 |
| 人工保存即标 reviewed | `src/application/use_cases/translation_tasks.py:edit_chunk` | 当前表示人工编辑过，未表达独立审校者、范围、未决问题与批准依据 |

这是一组有针对性的源码检查和反例验证，不是全仓库缺陷审计，也不估计实际译文中的错误发生率。

### 可复现的反例

2026-10-18，在上述基线、默认 `TranslationValidator`、空术语表下实测：

| 原文 | 人为构造的错误译文 | 当前结果 |
| --- | --- | --- |
| The method does not improve accuracy. | 该方法提高了准确率。 | passed=True |
| The result may suggest a correlation. | 该结果证明了因果关系。 | passed=True |
| Accuracy rose from 70 to 80. | 准确率从 80 提升至 70。 | passed=True |
| The method improves accuracy but doubles memory use. | 该方法提高了准确率。 | passed=True |
| 代码 `left = right + offset` | 代码 `right = left + offset`，均保留围栏 | passed=True |
| `[Paper](https://example.org/a)` | `[论文](https://example.org/b)` | passed=True |

作为对照，代码 `x = 1` 变成 `x = 2` 被数字缺失规则检出；并非所有代码修改都会漏检。

可在仓库根目录用 Python 重现，不需 API 密钥：

```python
from src.core.validator import TranslationValidator
from src.evaluation.consistency import AlignedSegment, compute_consistency
from src.evaluation.judge import parse_scores

validator = TranslationValidator()
cases = [
    ('The method does not improve accuracy.', '该方法提高了准确率。'),
    ('The result may suggest a correlation.', '该结果证明了因果关系。'),
    ('Accuracy rose from 70 to 80.', '准确率从 80 提升至 70。'),
    ('The method improves accuracy but doubles memory use.', '该方法提高了准确率。'),
    ('```python\nleft = right + offset\n```', '```python\nright = left + offset\n```'),
    ('[Paper](https://example.org/a)', '[论文](https://example.org/b)'),
]
for source, target in cases:
    print(validator.validate(source, target, {}).to_dict())

segments = [
    AlignedSegment(
        'The buried engine awakens. This is a shared note.',
        '埋藏引擎醒来。这是一条共同注释。',
    ),
    AlignedSegment(
        'A buried engine stops. This is a shared note.',
        '地下发动机停转。这是一条共同注释。',
    ),
]
print(compute_consistency(segments).as_dict())
print(parse_scores('{}').as_dict())
```

一致率反例实际产生 `rate=1.0`、`decision=no-rag`；`buried engine` 的 signature 是“。这是一条共同注释。”，没有对齐该短语的译法。空裁判 JSON 实际产生三个 3.0 分和 overall=3.0，并打印缺维度告警。

## 四、具体方法和工具

| 目的 | 方法 | 具体工具与现有接点 | 不能据此宣称什么 |
| --- | --- | --- | --- |
| 回溯原版 | 保存结构化提取结果、页区域和清理差异；疑点回看页图 | 已有 Marker/Pandoc；Marker JSON，PDF 页图及可选 PyMuPDF bbox；EPUB 保留原 XHTML 定位 | 两种提取器一致也不保证无 OCR 错误 |
| 保真格式 | 将自然语言节点与受保护节点分开；检查内容和引用身份 | Pandoc JSON AST；代码、公式、URL、引用 ID 等保存原始载荷并校验 | AST 结构正确不代表句意正确；公式保真不代表作者公式成立 |
| 术语可解释 | 按概念/义项记录译名、范围、例句和来源；旧 JSON 兼容导入 | 现有 SQLite 与术语表服务；先用结构化记录和精确查询 | 出现在术语表中不等于该译法正确 |
| 发现语义错误 | 逐句/分句核对，输出原译文跨度、类型、理由、引用证据；保留不确定状态 | 扩展 `QualityIssue` 和 `quality_pipeline`，使用结构化模型输出；模型建议由人工校准 | LLM 自评、不同模型共识和置信分都不是独立正确性保证 |
| 跨块核验 | 同一概念各次出现逐处对齐；核对缩写定义、指代、引文、符号与章节限定 | 扩展 `DocumentProfile` 保存带定位的定义索引；沿文档结构检索 | 公共中文子串不能直接当作术语译法 |
| 外部人评 | 定制 MQM 错误类别；系统匿名；两名领域双语审校者独立标注与第三人仲裁 | 导出标注供 Google Research 的 Marot 分析，或在已有审校页增加跨度标注；先选一种 | 人评有分歧，不能把仲裁意见称为普遍唯一正确译法 |
| 可复验比较 | 固定材料与版本、逐篇配对、多次运行、按文档计算不确定性 | 扩展现有 `translator-eval`；Python 统计和 JSONL 原始记录 | 多次 API 运行通常不能保证逐字重现 |

工具能力依据：[Marker 官方输出格式](https://github.com/datalab-to/marker#output-formats)、[Pandoc 官方 AST/过滤器说明](https://www.pandoc.org/filters.html)、[PyMuPDF 官方文本坐标说明](https://pymupdf.readthedocs.io/en/latest/app1.html)。选择这些工具是为了复用当前技术栈；没有证据要求先引入新的向量库、知识图谱或更多 Agent。

## 五、怎样修改，才对应上述要求

### 1. 先补证据与评测契约

保留两篇自撰样本作冒烟集。另建许可清楚的真实源文集合，覆盖完整章节或连续多页，保留公式、脚注、表格和真实跨块定义。按作品/论文划分开发集与留出集，防止相邻段落泄漏到两边。先用少量作品跑通标注协议，样本量由预期差异和区间宽度决定；不能把试点规模当充分统计证据。

先由两名领域双语审校者独立标注原有系统的错误和可接受变体，记录原文定位；开发集可用于调提示词，冻结的留出集只用于验证已选方案。领域专家资源未就绪时，如实保持“未验证”，不靠模型补签。

`src/evaluation/judge.py` 将缺维度、非法值、缺跨度或无依据的裁决记为无效/待复核，不能自动填正常分；报告展示全部计划样本、有效样本、翻译失败和裁判失败，避免只在幸存样本上报好成绩。异源裁判可以保留，但修改“避免偏好”为“仍需人工校准的自动辅助”。

### 2. 保留源文与转换历史

`document_converter.py` 的业务返回从单一 Markdown 路径逐步扩为转换产物：原文件指纹、结构树、原始提取、清理后内容、页图定位和工具版本。对清理器每次删除/合并记录变换，防止将正文、引文锚点、图文包装误作残留而无法追查。

在 `translation_models.py` 定义最少必要的数据契约：

- **原文定位**：源文件哈希、版本、块/段身份、PDF 页及区域或 EPUB 路径；同时保留派生 Markdown 的位置。
- **术语决策**：概念/义项 ID、英文、译名、允许变体、适用范围、原文证据、状态与决策版本。
- **质量问题**：原文/译文跨度、错误类型、严重性、理由、证据、检测者、所检查译文的哈希、未决状态。

这些是建议新增的概念，实施时需同步 `CONTEXT.md`，不能假装当前模型已支持。

`chunk_planning.py` 为每个块保留组成段落/节点的定位。先在块下增加可追踪的审校单元，继续沿用现有块级队列和并发；不必重写运行时。翻译与对齐允许一对多、多对一及未对齐，避免强迫两种语言一一对应。

### 3. 把“统一术语”深化为“有语境的术语决策”

将旧的 `dict[str, str]` 作为兼容入口，存储和选择层逐步支持概念/义项、作者/作品/章节范围及证据。没有出处的旧条目标为历史偏好，不能伪装为已核实标准。作者明确的用法与通行术语相冲突时记录冲突，由契约决定如何译。

`DocumentProfile` 保留摘要功能，另存带出处的定义与关键引用索引。只把当前块需要的记录注入翻译；若上下文不足，检索必要的原文定义或相邻段落，仍无法判定则提交复核。先验证结构化索引能解决哪些错误，再决定是否需要向量检索。

### 4. 独立检测与修复

保留规则检查并加强受保护载荷校验。数字核对至少包含出现位置、角色、单位、方向与比较对象；只看数字集合不够。代码和公式保留载荷，默认不交给模型改写；若契约允许翻译代码注释，单独定义可编辑区域。

在 `quality_pipeline.py` 增加语义审校路径，重点覆盖否定、条件、量词、指代、论证强度、漏译和增译。初期对开发/评测集全覆盖审校；生产既审高风险块，也随机抽查规则通过块，才能估计漏检。只有风险路由的召回率得到人评验证后，才压缩审校预算。

审校先产出问题和依据，修复再按问题提出补丁；验证器检查原有问题是否解决及是否新增严重问题。保留初译，不凭规则分数持平自动替换。不能稳定裁决时保留候选并进入人工复核。记录修复引入错误率、无效修复率和人工采纳率。

### 5. 建立真实的文档级一致性验证

将 `consistency.py` 的现有指标标为启发式候选，不再视为已验证的译法一致率。对每次术语/短语出现，保存原文位置与实际译文跨度，标明同义项还是不同义项；用人工标注集评估自动对齐和判定的准确率、召回率。相同错译应当“一致但错误”，合理语境变体应允许通过。

**需要重审 ADR-0002**：其 0.90 门槛直接驱动 RAG 立项/不立项，前提依赖该指标可信；现有反例否定了此前提。保留“不无条件上 RAG”的原则，将架构决定改为：已定位的跨块错误是否可由记忆解决，以及受控实验是否在质量和人工时间上有净收益。该建议是显式重开决策，不是本次已更改 ADR。

### 6. 让审校记录与导出携带证据

将任务执行状态、规则检查状态、语义审校状态和人工批准状态分开；运行完成不等于语义通过，未运行检查不应为 passed=True。当前 `reviewed` 兼容保留，其含义应明确为“人工编辑过”，另加审校者、时间、范围、依据和未决事项；编辑不自动等于独立复核。

扩展现有双语审校页：选中译句可跳到原文页区域/EPUB 段落，查看对应术语依据、初译与修订差异、尚未解决的质量问题。只围绕审校任务加必要信息，无需新建另一套工作台。

沿用现有结果目录和 SQLite，增加版本化的旁车记录：运行清单、源文定位、术语决策、问题及修订历史。缓存继续复用，但将生成所需依赖与验证版本区分：评测规则更新后可只重验，原文、术语义项或已用上下文变更时使相关译文及批准状态过期；不能继承旧的通过结论。

## 六、你我之外，什么能支持结果可信

| 证据层 | 证明范围 | 建议验收方式 |

| 文件与结构核对 | 本次译文使用的是哪个源版本，受保护内容是否一致 | 哈希和原版定位可复查；受保护载荷满足预先约定的不变量；已知 OCR/清理疑点全部解决或显式列出 |

采用适配任务的 MQM 类错误类型并记录 critical/major/minor，权重和分母提前固定；自定义权重不能冒称为官方唯一标准。准确性错误与流畅度分别展示，不靠综合分掩盖严重失真。人工标注要报告一致性与分歧，不将“人工抽检主观”当成排除它的理由。

统计单位应尊重文档内相关性；不能把同一本书几百块当几百个独立作品。重复生成用于观察模型波动，增加独立作品用于观察跨文本泛化，两者不能互相替代。真实人评与第三方复验尚未执行前，不能声称新设计已证明有效。

## 七、实施顺序与停止条件

1. **固定现状和错误标注协议**：保存这些反例、旧系统真实输出、真实源文及人工基线；先改评测缺失处理与报告口径。产物是别人能看懂且能复查的基线，不能只有分数表。
2. **打通一个垂直切片**：在一个限定领域的一篇完整材料上，实现原文定位 → 带证据术语 → 翻译 → 问题跨度 → 修复差异 → 人工裁决 → 带旁车记录导出。复用队列、缓存和界面。通过后再推广到其他文档。
3. **验证语义审校与文档一致性**：对照原基线、人评标注及正确变体，分别量化漏检、误报、修复引入错误和跨块问题，校准风险路由。
4. **冻结方案后做留出评测**：报告按领域/作品的错误数、区间、人工时间、成本与失败率。某一领域无增益就缩小宣称范围；收益不确定就增加独立材料或修正机制。

建议的发布契约包括：受保护载荷无未经授权变更；没有未解决的已知 critical 问题；低严重性问题及未覆盖检查明确列出；质量主张限定到真实验证过的材料与范围。观察到零个严重错误并不证明未来零错误。具体允许的 major 密度与漏检风险应由用途和人评校准决定，不能凭空设“95% 准确”。

暂缓与上述证据闭环无关的功能扩展。LangGraph/native 的等价性和运行可靠性仍应作为工程回归检查；只有翻译机制改变的实验才用来解释翻译质量。框架更换本身不构成质量改进证据。
