# 产品升级调研：从"能翻译整本书"到"可信、可对照、可回溯的书籍翻译工作台"

日期：2026-11-09
范围：现状盘点 → 目标差距 → 技术方案 → 体验提升建议 → 分阶段路线图

---

## 0. 一句话定位（建议）

> **LLM 已经翻译得足够好，难的是"整本书"：结构不能丢、术语不能飘、失败不能重来、结果必须可核对。**
> agentic-translator 把一本书变成可追溯的「原文段 ↔ 译文段」映射，结构由程序保证、语义由多 Agent 校对、质量由人工可抽查。

这个定位比"多 Agent 翻译系统"更能打：它直接回答了"为什么不直接把书丢给 ChatGPT"。

## 1. 现状盘点：已经做到什么程度

| 痛点 | 现状 | 评价 |
| --- | --- | --- |
| 长书无法一次翻译 | `ChunkPlanner` 章节感知切块（默认 3600 字符，按标题/代码围栏切，超长块按句切），携带前一块末尾 1400 字符作上下文 | ✅ 基础扎实 |
| 失败不能整本重来 | chunk 级 SQLite 缓存（键含模型/术语表/Prompt 版本/画像指纹）、任务租约 + execution_id、失败块写占位符、Web 端可逐块重译 | ✅ 做得很好，是亮点 |
| 术语前后一致 | 术语表注入（按块只注入相关术语）、术语 Agent 自动起草术语表、分析员抽样首/中/尾生成文档画像（摘要/风格/术语提示） | ✅ 有；⚠️ 缺"全书级"一致性审计 |
| 公式/图片/标题/链接不丢不错位 | **靠 LLM 自觉保留** + `TranslationValidator` 用正则**数个数**（标题、图片、链接、代码围栏），公式做字符串包含检查 | ⚠️ 是最大短板，见 §2.1 |
| 多 Agent 逐块比对 | 分析员 → 翻译员 → 规则质检 → 审校员（仅对不通过块整块重译一次，择优保留） | ⚠️ "比对"由规则完成，审校是整块重写 |
| 双语对照导出 | 双语 Markdown（原文引用块 + 译文 + `---`）、双栏 HTML（再用正则把双语 Markdown 拆回来） | ⚠️ 对齐粒度是**整块（~3600 字符）**，不是段落；解析脆弱 |
| 点击跳转对应位置 | Web 审校页有逐块左右两栏 + `id=chunk-N` 锚点；HTML 导出无联动 | ❌ 未实现 |
| 脚注 | 无专门处理 | ❌ 未实现 |
| 目录 | `SmartMarkdownFormatter._clean_toc_lines` 只做清理 | ⚠️ 且锚点会被破坏，见 §2.4 |
| 评测 | 有 LLM-as-judge 三组对照 + 一致率指标框架 | ⚠️ `docs/evals/results/report.md` 目前**只有 dry-run 占位数据** |
| 工程化 | LangGraph 编排、FastAPI + Worker、Docker、CI、MCP Server、Langfuse | ✅ 作品集加分项齐全 |

**结论**：系统的"可靠性骨架"（并发、限流、缓存、租约、恢复、审校工作台）已经是作品集水准；短板集中在**结构保真的方法论**和**对照/跳转的粒度**——而这恰恰是你产品定位里最核心的卖点。

## 2. 关键差距与问题（读代码发现的具体问题）

### 2.1 结构保真依赖 LLM，校验只数个数

- `prompt_builder.py`：要求 LLM "完整保留所有 Markdown 格式"——这是**请求**，不是**保证**。
- `validator.py::_check_markdown_structure`：只比较标题/图片/链接/代码围栏的**数量**。以下错误都检测不到：
  - 图片顺序互换、图片挪到另一段（数量不变）；
  - 链接 URL 被 LLM 改写/截断（`[文本](url)` 数量不变）；
  - 标题层级 `##` 变 `###`（`^#{1,6}` 都算标题）；
  - 表格行列错位、列表层级变化、脚注引用 `[^3]` 丢失或编号错乱；
  - `\[...\]`、`\begin{equation}`、`\(...\)` 形式的公式（只检查 `$` / `$$`）。

### 2.2 双语对齐粒度太粗

- `OutputManager._format_bilingual` 以**整个 chunk** 为单位：一段 3600 字符的原文配一段译文。人工抽查时仍需在几十行里自己找对应句——"可对照"名不副实。
- `ExportService.parse_bilingual_markdown` 再用 `\n---+\n` 和 `>` 前缀**反向解析**双语 Markdown 生成 HTML。原文本身含引用块或水平分隔线时会错位；还有"原文需含 4 个连续字母"等启发式过滤，可能静默丢段。
- 根因：**没有一份结构化的中间表示（IR）作为唯一事实来源**，导出格式之间互相解析。

### 2.3 审校是"整块重译"，不是"定点修复"

- `quality_pipeline.repair` 把整块原文 + 译文 + 问题清单丢给审校员重写，可能把原本正确的部分改坏（虽有 `is_better` 择优，但只按问题严重度计分）。
- 规则质检擅长结构，LLM 擅长语义（漏译、误译、逻辑反转）；目前**没有语义层面的检查 Agent**。

### 2.4 目录与内部链接会断

- `markdown_formatter._clean_links` 会把 `[文本](url){#id .class}` 的属性块删掉；pandoc 从 EPUB 转出的标题锚点、脚注锚点就藏在这些属性里。目录里的 `(#ch01-sec2)` 链接于是指向不存在的 id。
- 标题翻译后，基于标题文本自动生成的 slug 也会变化，内部跳转失效。

### 2.5 其他

- 评测报告是 dry-run，ADR-0002 的 RAG 决策还没有真实数据——作为展示项目，"有评测框架但没有数字"是明显漏洞。
- `src/core/*` 与 `src/domain|infrastructure/*` 存在过渡期重复（`core/chunk_planner.py` 等是转发壳），`src/converters` 与 `src/infrastructure/converters` 并存；`CLAUDE.md` 中的参数（2000 字符/块、检查前 5 个术语）已与代码（3600 / 25）不符。

## 3. 核心技术方案：引入"文档中间表示（Document IR）"

这是整个升级的地基，后面的公式保真、段落级对照、点击跳转、脚注、目录**全部建立在它上面**。

### 3.1 思路：结构由程序持有，LLM 只看到"带占位符的文字"

专业 CAT 工具（Trados、memoQ、XLIFF 标准）几十年前就这样做：把文档拆成**段（segment）**，段内的格式/公式/链接替换成**内联标签**，译者（现在是 LLM）只翻译文字并原样搬运标签，最后由程序还原。

```
原文段：  The [CCRU](http://ccru.net) defined **hyperstition** as $f(x)=x^2$ [^3].
送给 LLM：The <a1>CCRU</a1> defined <b1>hyperstition</b1> as <m1/> <fn3/>.
LLM 返回：<a1>CCRU</a1> 将 <b1>超虚构</b1> 定义为 <m1/><fn3/>。
程序还原：[CCRU](http://ccru.net) 将 **超虚构** 定义为 $f(x)=x^2$[^3]。
```

收益：
- **公式、URL、图片路径、代码、脚注编号 LLM 根本看不到原文**，物理上无法改错；
- 校验从"数个数"升级为"**标签集合与嵌套关系完全一致**"——确定性、零成本、零误报；
- 允许语序调整（成对标签 `<b1>…</b1>` 可以在句中移动），这是纯"保护区"方案做不到的。

### 3.2 IR 选型

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| **pandoc JSON AST**（`pandoc -t json`） | 已是依赖；EPUB→AST 无损保留锚点 id、脚注（`Note`）、表格、公式（`Math`）、引用；可直接从 AST 输出 Markdown / HTML / **EPUB** / docx | 需要写 AST 遍历；PDF 路径需先经 marker 得到 Markdown 再进 pandoc | ✅ **首选** |
| markdown-it-py token 流 | 已是依赖，Python 原生 | 不覆盖 pandoc 扩展语法（属性、脚注定义需插件），回写 Markdown 要自己做 | 备选 |
| 自定义正则切段 | 改动小 | 就是现在的问题来源 | ❌ |

建议的 IR 数据模型（落库即为审校与导出的唯一事实来源）：

```text
Document
 └─ Block(block_id="b-0123", type=Para|Header(level,anchor)|Table|Figure|Math|Code|Footnote|ListItem,
          section_path, source_locator={pdf_page, bbox} | {epub_spine, href})
     └─ Segment(seg_id="b-0123.s2", source_text_with_tags, tags={m1: "$f(x)$", a1: "http://..."},
                translation_with_tags, status, quality_report, history[])
```

- **Block** 是段落/标题/表格等结构单元，`Code`、`Math`、`Figure` 类型直接跳过翻译；
- **Segment** 是翻译与对照的最小单位（默认 = 段落；超长段落按句切）；
- **Chunk 退化为"调度批次"**：仍按 ~3600 字符打包若干段送进一次 LLM 调用（保持上下文与成本），但输出要求按 `seg_id` 返回（JSON 或 `<seg id=…>` 包裹），逐段还原、逐段校验、逐段重试；
- 现有缓存、租约、TranslationResult 只需把粒度从 chunk 下沉到 segment（或保持 chunk 缓存 + segment 级结果表）。

### 3.3 PDF 路径

- marker 除 Markdown 外支持 JSON 输出（含块类型、页码、多边形坐标）；MinerU、Docling 也提供带版面坐标的结构化输出，且对公式（输出 LaTeX）通常更强。建议**做一层转换器抽象**，把这些结构化输出统一映射为 IR，并保存 `source_locator={page, bbox}`——这是 §4 "点击跳回 PDF 原页"的前提。
- 选型需用你自己的 2～3 本典型书（含公式的 ML 论文、扫描质量一般的哲学书）做一次横评：公式识别率、阅读顺序、脚注识别、速度。

## 4. 你提出的需求逐项方案

### 4.1 公式 / 图片 / 标题层级 / 链接 / 目录：不丢、不错位

| 元素 | 方案 | 校验 |
| --- | --- | --- |
| 行内/行间公式（`$`、`$$`、`\(\)`、`\[\]`、`equation` 环境） | IR 中为 `Math` 节点 → 占位 `<m1/>`；行间公式整块不送 LLM | 标签全等；渲染期 KaTeX 试编译，失败标红 |
| 图片 | `Figure` 块不翻译；**图注（caption）单独作为段翻译**；alt 文本可选翻译 | 图片序列（路径列表）顺序全等 |
| 链接 | URL 进标签表，仅锚文本可译 | URL 列表顺序全等 |
| 标题层级 | `Header(level, anchor)` 程序持有，LLM 只译标题文字 | 层级序列全等 |
| 目录 | **不翻译目录本身**：从译后标题树重新生成；原锚点 id 保持不变（不要用中文 slug） | 所有 `#anchor` 链接在输出中可解析（死链检查） |
| 表格 | 逐单元格作为段翻译，行列结构程序持有 | 行列数全等 |
| 代码 | 跳过；可选只翻译注释 | 字节级全等 |

关键动作：**修掉 `_clean_links` 删除锚点属性的行为**，或在 IR 路径下完全绕开该格式化器。

### 4.2 术语与风格全书一致

已有：分析员画像 + 术语表 + 术语 Agent。建议补三件：

1. **术语账本（Term Ledger）**：翻译过程中，每个段返回"本段新出现的专有名词及译法"（结构化字段）。首次出现即登记，后续块的 Prompt 注入"已确立译法"。这把"术语表外的一致性"从事后统计变为事中约束，也是 ADR-0002 的 RAG 的轻量替代品。
2. **全书一致性审计（Consistency Auditor，后处理 Agent）**：对每个术语表词条/账本词条，扫描全部译文，列出"同一原词的不同译法"和出现位置，一键统一替换（在 IR 上做，不会误伤公式与链接）。
3. **术语变更影响分析**：用户在审校中修改某个术语 → 系统根据 IR 精确知道哪些段包含该原词 → **只重译这些段**（或直接做确定性替换），而不是整本重跑。这是非常好的展示点："改一个术语，3 秒定位 47 处，一键更新"。

### 4.3 长书失败不重来

现有机制已足够好。增量建议：
- 重试/重译粒度从 chunk 下沉到 segment；
- **运行前成本预估**（总 token、预计费用、预计耗时）与预算上限，超支自动暂停；
- 失败段在双语 HTML 中高亮且可筛选，而非仅占位文本。

### 4.4 多 Agent 逐块比对

建议把"比对"拆成**确定性层**与**语义层**，诚实地说明为什么不把一切都交给 LLM：

| 层 | 执行者 | 检查内容 | 成本 |
| --- | --- | --- | --- |
| 结构层 | 程序（IR 标签比对） | 公式、图片、链接、标题、表格、脚注引用、数字 | 0 token，确定性 |
| 术语层 | 程序 + 术语账本 | 术语表与账本译法是否命中 | 0 token |
| 语义层 | **Critic Agent**（异源模型更佳） | 漏译、增译、误译、否定/逻辑反转、语气 | 仅对抽样或高风险段 |
| 修复层 | Reviewer Agent | **只改被点名的段**，返回 diff 而非全文 | 按需 |

- 高风险段判定：结构层失败、长度比异常（中英字符比偏离均值 2σ）、含否定词/数字、Critic 打低分。
- 修复改为"段级 + 带理由"：Reviewer 输出 `{seg_id, new_translation, reason}`，前端可展示"修复前/后 diff + 理由"，人工一键接受/拒绝。
- 这样多 Agent 的价值是可量化的：评测里能直接给出"结构层拦截 X%、语义层拦截 Y%、修复成功率 Z%"。

### 4.5 双语 Markdown 与双栏 HTML：段落级对照

- 从 IR 直接渲染，不再相互解析；对齐单位为 **segment**（段落），而不是 3600 字符的 chunk。
- 双语 Markdown：每段原文/译文相邻，可选"仅译文 + 原文折叠（`<details>`）"模式；
- 双栏 HTML：左右两栏 **各自连续排版**（像读书），而非每段一个卡片（像表格），通过 seg_id 联动（见 4.7）；
- 另加**双语 EPUB 导出**（原文段 + 译文段交替，或"译文为主、原文小字"），这是读书场景用户真正会用的格式，pandoc 从 IR 可直接产出。

### 4.6 脚注

| 场景 | 处理 |
| --- | --- |
| 脚注引用 `[^3]` | 占位标签 `<fn3/>`，位置随语序移动但不可丢失 |
| 脚注正文 | IR 中独立 `Footnote` 块，作为独立段翻译；**Prompt 注入其被引用的那一段原文作为上下文**（避免脚注脱离语境误译） |
| EPUB 尾注（集中在章末/书末，以链接互指） | 转换阶段识别"回链"模式，规范化为 pandoc 脚注；保留双向锚点 |
| PDF 页脚脚注 | 依赖解析器识别（marker/MinerU 的 footnote 块类型），按页内上标编号挂回正文 |
| 译者注（译注） | 新增类型：Critic/Translator 可提出"需要译注"的建议（文化背景、双关、术语解释），**默认不自动插入**，进入审校队列人工确认；渲染为区别于原注的样式（如"〔译注〕"） |
| HTML 展示 | 悬停/点击弹出脚注卡片，不打断阅读 |

### 4.7 "像 LaTeX SyncTeX 一样"点击跳转

把它做成三层，逐层递进：

1. **原文段 ↔ 译文段双向跳转（必做，依赖 IR 的 seg_id）**
   - 两栏每段都带 `data-seg="b-0123.s2"`；点击任一侧 → 另一侧 `scrollIntoView` 并高亮；悬停时两侧同时浅色高亮。
   - "跟随滚动"开关：用 `IntersectionObserver` 计算视口中心段，另一栏平滑对齐到同一段（两栏长度不同，不能按像素比例同步，必须按段锚点同步）。
   - 句级（可选）：段内再按句切 + 对齐（可让 LLM 在输出时带句号标签，或用 bertalign 等句对齐算法），点击句子高亮对应句。
2. **跳回原始文件位置（真正的 SyncTeX 体验）**
   - PDF：IR 保存 `{page, bbox}`，前端用 pdf.js 打开原 PDF，跳到对应页并在 bbox 画高亮框；反向：在 PDF 上点击 → 找到包含该坐标的块 → 跳到译文。
   - EPUB：保存 spine/href + 原始元素 id，可在 epub.js 阅读器中定位。
3. **审校闭环**：在任一跳转位置都能直接"编辑译文 / 加入术语表 / 标记问题 / 请 Agent 重译此段"。

导出的双栏 HTML 也应内嵌这套联动（单文件、离线可用），这样分享给别人的成果本身就是可交互的对照阅读器。

### 4.8 可自定义项（梳理成"翻译配置档"）

建议把散落的配置收敛为一份**项目级 Translation Profile**，Web 端可视化编辑、可保存为模板复用：

- 领域预设（哲学 / ML 论文 / 技术文档 / 小说）→ 对应 Prompt、风格、切块参数；
- 术语表（多个可叠加，有优先级）+ 禁译词表（保留原文不译的词）；
- 风格：直译 ↔ 意译滑杆、正式度、人名/专名首次出现是否括注英文、标点规范（全角/半角、中英文间空格）；
- 结构：是否翻译图注/alt/表格/代码注释、脚注策略、是否允许译注；
- 质量：是否启用 Critic、抽样比例、修复次数、预算上限；
- 输出：单语 / 双语 MD / 双栏 HTML / EPUB / 双语 EPUB / PDF。

## 5. 额外的体验提升建议（按价值排序）

1. **"先试译一章"再整本跑**：分析完成后先翻第一章（或抽 5 段），用户确认风格与术语后再全量。避免跑完 300 块才发现风格不对——这是长书翻译最大的隐性成本。
2. **术语表在审校页内联编辑**：在译文中选中一个词 → "加入术语表"，自动带出原文对应词（靠段对齐）→ 弹出影响范围 → 一键应用（§4.2-3）。
3. **人工修改反哺**：用户手改的段落被记录为高置信样本；系统从修改中归纳偏好（"总把 X 改成 Y"）并提示加入术语表/风格规则。
4. **版本与 diff**：每段保留历史（初译 / 修复 / 人工），可对比、可回滚；全书级"本次修改了哪些段"。
5. **质量热力图**：目录树上按章节显示通过率、风险段数量，审校时按风险从高到低走，而不是从头翻到尾。
6. **键盘驱动审校**：`j/k` 上下段、`e` 编辑、`a` 接受、`r` 重译——审校几百段时效率差距很大。
7. **双语全文搜索**：同时搜原文与译文，结果在两栏同步高亮（查某术语所有出现处非常有用）。
8. **阅读模式**：仅译文、排版舒适、悬停任一段显示原文浮层——"读者视角"而不是"审校视角"。
9. **成本/进度透明**：实时 token、费用、每段耗时；Langfuse 已接入，可在任务页嵌入摘要。
10. **公开 Demo**：用公版书（如古腾堡计划中的英文哲学/科学著作）做一份完整的在线双栏对照成品，挂在 README 第一屏。展示项目最有说服力的是"打开就能点"的成品，而不是截图。

## 6. 竞品 / 参考实现（定位差异）

> 以下为方向性梳理，功能细节以各项目最新版本为准，正式写进 README 前建议逐一核实。

| 类别 | 代表 | 它们擅长 | 本项目的差异化 |
| --- | --- | --- | --- |
| 浏览器/阅读器双语 | 沉浸式翻译 | 网页、PDF、EPUB 段落级双语阅读，体验好 | 偏"即时阅读"，缺全书术语一致性、质检与可审校工作流 |
| PDF 版面保持翻译 | PDFMathTranslate / BabelDOC | 保留 PDF 原版面与公式 | 输出仍是版面，不利于结构化编辑与再导出；术语治理弱 |
| EPUB 双语制作 | bilingual_book_maker 等 | 简单好用的双语电子书 | 无结构校验、无多 Agent 审校、失败恢复弱 |
| 文档翻译服务 | DeepL 文档翻译 | 格式保留好、稳定 | 黑盒、术语控制有限、长书昂贵、不可审校 |
| 专业 CAT 工具 | Trados / memoQ / OmegaT | 段、内联标签、翻译记忆、QA 的成熟方法论 | 面向人工译者，LLM 整合与自动化弱 |
| PDF 解析 | marker / MinerU / Docling | 版面分析、公式转 LaTeX | 作为上游输入，可插拔 |

**定位总结**：本项目 = CAT 工具的方法论（段、标签、术语、QA） + LLM 多 Agent 自动化 + 面向整本书的可靠调度 + 可交互的对照审校。这个组合在开源里是空位。

## 7. 展示（作品集）层面的建议

1. **补真实评测数字**，并新增一项最能体现卖点的指标——**结构保真率**：
   - 构造基准：选若干含公式/图片/脚注/表格/内链的章节；
   - 对比三组：① 直接把章节丢给同一 LLM ② 现有系统 ③ IR + 标签方案；
   - 指标：公式保真率、链接/图片完整率、标题层级正确率、脚注完整率、死链数、术语一致率、LLM-judge 质量分、成本。
   - 一张"裸 LLM vs 本系统"的对比表比任何架构图都有说服力。
2. **完成 ADR-0002 的真实数据回填**（或在术语账本落地后改写该 ADR）。
3. README 第一屏：一句话定位 + 交互 Demo 链接 + 对比表 + 一张联动跳转的 GIF。
4. 清理过渡期重复模块（`src/core` 转发壳、`src/converters`），更新 `CLAUDE.md` 中过时参数——面试官会看代码。
5. 为 IR 引入写一份 ADR-0004（为何从"LLM 保留 Markdown"转向"程序持有结构 + 内联标签"），这是很好的技术叙事。

## 8. 分阶段路线图

| 阶段 | 内容 | 产出 / 验收 |
| --- | --- | --- |
| **P0 地基** | Document IR（pandoc AST）+ 段切分 + 内联标签编解码 + 段级结构校验；chunk 退化为调度批次；结果表下沉到段 | 结构保真基准上公式/链接/图片完整率 ≈100%；ADR-0004 |
| **P1 对照与跳转** | 从 IR 渲染段级双语 MD / 双栏 HTML（两栏连续排版 + data-seg 联动 + 跟随滚动）；锚点保留与目录重建；死链检查 | 导出 HTML 离线可点击双向跳转；内部链接 0 死链 |
| **P2 脚注与表格** | 脚注块化 + 引用上下文翻译 + 悬浮卡片；EPUB 尾注规范化；表格逐格翻译；译注建议队列 | 脚注完整率指标 |
| **P3 一致性与多 Agent** | 术语账本、全书一致性审计、术语变更影响分析；Critic Agent + 段级 diff 修复 | 评测给出各层拦截率与修复成功率 |
| **P4 体验** | 先试译一章、内联加术语、版本 diff、质量热力图、键盘审校、双语搜索、阅读模式、成本预估 | 可用性走查 |
| **P5 回溯原文** | PDF 结构化解析（保存 page/bbox）+ pdf.js 定位高亮；EPUB 定位；双语 EPUB 导出 | SyncTeX 式跳转 Demo |
| **P6 展示** | 真实评测 + 对比表 + 公开 Demo + README 重写 | 作品集上线 |

建议先做 P0 + P1：它们决定了后续所有功能能否成立，而且本身就足以形成"裸 LLM 做不到"的鲜明对比。
